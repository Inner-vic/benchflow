# Jenkins 发包

2026-11-17起，默认只执行原Jenkins的一次普通APP发包。沿用pcm-dual-package目录和调用名兼容已有引用；用户可见名称统一为“Jenkins 发包”。当前流程见[Jenkins 发包说明](../../docs/17-Jenkins发包.md)。

当前Bot源码已适配Jenkins发包，使用pcm_release.py的pcm-bot-release/v2计划和“确认发包”按钮；代码尚未部署验收。先核对生产版本，不能用旧“确认构建两版APP”按钮执行当前任务。v1计划只用于恢复已确认历史任务，不允许新建旧流程任务。

## 1. 收集本次输入

保留已经约定的输入方式：

- 源码分支地址：本次uroad GitLab分支链接，明确仓库和分支。
- 软件版本：本次BASE_LINE，四位十六进制字符，可带SW前缀；新任务明确填写，不沿用旧包版本。
- 构建类型：release/debug，默认release，最终值须展示。
- 组件版本配置APP_VERSION：本人上次确认的配置作为编辑起点，首次为空版本模板；conan_shared、uroad_m100、dag_compiler三项精确引用必填，其他组件可逐行追加。

软件ID按已确认的AVM范围固定0111。用户无需填OFF/ON两套参数，也不为本次发包提供数据集、传感器SO或台架执行目标。配置确认不等于授权提交构建；账号凭据不进卡片或仓库。

## 2. 只读核对源码与原参数

读取本次分支、所填组件的精确配方及匹配成功基线，记录真实源码Commit和版本来源。可以复用scripts/resolve_pcm_input.py的规范化和scripts/source_build_discovery.py的只读发现能力；不调用旧pcm_dual_config.py、plan_from_card.py生成默认任务；Bot新任务应由pcm_release.py生成，交给已适配的Engine和独立软件worker。

核对所选uroad_m100精确配方中的取码仓库与源码提交，必须与本次分支确认的Commit一致；版本名、配方摘要通过或依赖匹配均不能替代源码对应性证明。动态取码无法确定提交、引用不匹配或组件未发布时，先补齐原组件CI发布及精确来源证据，再审阅最终参数，不按旧版本直接发包。verify_recipe仅证明配方存在与摘要；pcm_release.binding另读精确配方和CMake进行源码及OFF模式核验。source_build_discovery的common_inputs会单独保存M100引用，最终APP_VERSION须由当前适配器补齐，不能直接提交漏掉M100的common_app_refs。

按原Job当前参数和用户最终组件配置，准备一份APP_VERSION及一份LOCKED_LIBS。用户填写的uroad_m100引用用于这次正常APP构建，不替换成自动生成的OFF/ON私有版本，不因后续评测用途改写CMake、发布两份配方或先冷编译两份M100。核实所选普通组件的实际编译模式；若引用是评测版或与用户目标不符，说明具体不符并核对正确普通版引用，不暗中修改共享配方。

核对三项固定引用的版本、追加组件、SDK/消息库及配套依赖；APP_VERSION不决定集成范围，仍以原集成package.lst为准。两栏同名冲突、缺项、版本范围、无法确认的源码身份或无权限时报告具体缺项，不猜最新版本、不套用旧基线。

BASE_LINE、BUILDVARIANT、CONTROLLER、MANIFEST_NAME、通知、镜像/Portal及其他参数按本次实际来源核验，保留未知项的原维护配置。MANIFEST_NAME是参考基线制品，不是本次新包文件名。目标为APP普包，确认基线未继承本次不需要的镜像或Portal动作。BUILD_REPLAY不是评测输出开关。

## 3. 沿用高鹏原流程，只提交一次

固定完整Job为TRANSIT/XCU/SCM/CCU-ACORE-RELEASE-BUILD。读[原流程复用说明](references/upstream-workflow.md)：有已安装的高鹏Skill时读取并沿用，没有时使用随附来源说明，不声称已安装。

区分执行入口：原Skill的浏览器流程使用已登录的本人Jenkins会话；当前Bot后台使用工作站预配置认证，不能把浏览器登录或飞书操作者当作后台发起身份。核对实际Job、预填参数表，完整展示本次输入、最终APP_VERSION/LOCKED_LIBS、构建类型、版本编号、上传与通知去向。用户修改后重新读取并审阅。最终状态获得本次有效授权后，浏览器流程只点击一次Build；Bot流程只由真实“确认发包”回调入队，worker提交冻结参数，助手不再另行点击或调用提交接口。

记录本次提交意图、真实queue或跳转返回的构建编号；提交未知时先查原身份，不能重复点击或用lastBuild猜测。失败交付实际错误和已有产物，不自动补发另一版、改共享流水线或取消其他任务。旧软件准备/计划工具的内部状态不是本流程已提交Jenkins的证据。

## 4. 发包交付

一次成功构建交付：一份LIVC APP普包、对应标准Conan Lockfile、同一次真实构建链接及下载校验值。原Jenkins按既有配置发送本次的一张正式卡片；通知接收人和群以原Job实际配置及真实构建身份为准，不自行额外发送群消息或私信。

本次不生成OFF/ON成对清单，不进行成对比较，不执行第二次Build。没有真实构建时只报告整理、校验或计划，不能生成假包链接。

## 5. 台架阶段保持独立

用户按原入口转发本次构建卡片，后续再核齐数据、相机/雷达SO、M100及运行配置，单独确认台架任务。发包不自动创建台架任务、替换依赖或编译评测M100，也不复用软件构建确认代替台架确认。

评测目标是在本APP配套源码和依赖上开启ON，复用原build.sh生成评测M100，再按材料流程装配，见[目标步骤与接入状态](../../docs/18-M100编译流程.md)。既有自动程序仍保留APP官方模式，见[官方规则](../../docs/11-M100官方构建与自动编译.md)；独立评测变体及装配尚待适配，不按目标文档擅自改变当前模式保护或已确认任务，不承诺普通APP转发后自动获得评测能力。
