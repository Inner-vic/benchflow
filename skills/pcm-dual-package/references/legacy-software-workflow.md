# M100 构建与 Jenkins 交付

沿用 `pcm-dual-package` 名称兼容已有调用，不再默认生成两个 APP。本 Skill 处理软件准备；现有台架材料确认、FIFO、Runner 和评测器继续各自负责原业务，不因本 Skill 被调用而自动执行。

用户明确进入 **PCM 双版本构建** 时，使用[独立功能](pcm-dual-feature.md)：同一源码交付普通版 OFF、评测版 ON 两份 APP，固定 `delivery=app_pair`，不套用普通软件准备入口的单 APP 默认。卡片收源码分支链接、本次软件版本、构建类型和本人组件版本；软件版本不得从历史构建默认继承。用户已明确本入口全部为AVM，SOFTWARE_BRANCH固定0111，不再要求输入；旧表单不能改成其他ID。组件区仅列conan_shared、uroad_m100、dag_compiler三个必填引用，版本必须填写，其他组件可追加。uroad_m100作为M100配方/版本基准与本次源码一起冻结，不作为旧SO复用，也不重复加入公共APP_VERSION。按钮“校验构建配置”仅校验；通过后展示两版完整最终参数，用户点击“确认构建两版APP”才进入独立软件FIFO，自动发布本次私有配方，由原Jenkins依次编译并打包OFF/ON，更新两张结果卡。该功能与原台架材料卡分开，不能复用其执行确认或队列。部署、恢复和验证边界见[构建确认与派发](../../../docs/16-双版本构建确认与派发.md)。

当前独立双APP入口只验收软件构建与结果卡交付；台架评测是另一个阶段，须人工转发所选结果卡作为输入。共用Bot不等于两个workflow已自动整合。

## 先分清四件事

| 维度 | 含义 | 禁止混用 |
|---|---|---|
| M100 编译模式 | `WITH_EVAL_DUMP` 是否编入离线辅助代码 | 不能称仅控制保存文件，也不是指标评测开关 |
| 运行配置 | YAML 的 `eval_dump.enable` 及场景、输出等配置 | ON SO 不等于运行功能已开启；不要修改共享配置 |
| 软件交付 | 仅 SO、一份基础 APP 加配套 SO、两份完整 APP | 编译 ON/OFF 两个 SO 不等于必须打两次 APP |
| 台架目标 | 仅回放，或回放后评测 | 不据此暗中翻转已有 APP 的官方编译模式 |

按本次准确源码核对控制点：宏可能覆盖预测落盘、多场景协调、标定重载和部分数据处理路径，不保证两版仅输出文件不同。其他调试输出和 `input_traj`、`sus_preview_timeline.csv` 分别核对，不承诺一个开关使产物齐全。

## 1. 确定软件来源

- **已有 APP**：由 APP、构建链接及集成 Lockfile 定位精确 M100 配方修订、源码 Commit 和依赖。保留官方模式；上传成品先校验，缺成品再按配套来源编译。该路径不变成新发包，不重新使用旧 APP 的 M100。
- **源码构建**：仓库与分支分别输入，也兼容完整分支链接。仓库可识别 `uroad` 或公司 GitLab 完整路径；当前 Job 只核验过 uroad，其他仓库先做兼容核查，不静默替换仓库。使用 `scripts/resolve_pcm_input.py` 规范化输入，再按[源码自动解析与确认](source-input-review.md)运行只读发现。分支必须明确，不默认 master/main；每次解析重新固定 Commit。基线、产品配置、软件 ID、conan_shared 和依赖从本次源码与成功基线锁解析，不固定使用任何历史版本。

源码模式下，用户明确要求 ON/OFF 时准备两份编译变体；只有一份需求时只准备一份。分支名不等于版本号；最近标签只能作为命名参考，不能冒充当前提交已发布版本。

读[依赖解析](dependency-resolution.md)及[组件选择](component-selection.md)。运行 SO 不能代替开发头文件。缺接口时定位实际源码和配方，不因库名一样就复用；现成配套组件优先，不无依据更换版本。

## 2. 决定交付范围，再生成计划

| 用户目的 | 内部 delivery | Jenkins APP 数 |
|---|---|---:|
| 只编译或比较 ON/OFF M100 | `components_only` | 0 |
| Jenkins 发一份基础 APP，同时准备切换用的 M100 | `single_app_with_variants` | 1 |
| 明确要求普通版、评测版各一个可直接部署的 APP | `app_pair` | 2 |

“Jenkins发包加ON/OFF M100”未明确要求双 APP 时，按本次已对齐的一份基础 APP 加配套 SO 方案处理。基础 APP 模式从准确源码/配方的已核验默认值确定并展示；若无明确默认或用户另选变体，再澄清，不按评测目标猜。仅提出 ON/OFF 不触发两个 Jenkins Build。

新请求先按[工作流上下文](workflow-state.md)填写内部 context，再运行：

```sh
python <skill>/scripts/pcm_workflow.py --context <工作站/context.json> --output <新的工作站/plan.json>
```

计划工具不联网、不编译、不发布、不提交 CI、不写网关任务。未编译、未发布或基线属性未核对时，`jenkins_modes` 为空。`pcm_existing_job.py` 只用于**明确选择 app_pair 的旧双包状态跟踪**，不能绕过新计划把单 APP 任务变成两次发包。

先展示本次仓库、分支、Commit、选定基线、依赖精确引用和完整最终 Jenkins 参数，再由用户确认构建。`build_review` 可展示尚待编译/发布但引用已确定的计划；确认不是编译通过。确认后才编译和发布，实际提交前仍须满足 `require_app_review` 的真实收据门禁，并通过 `ready_parameters_after_confirmation` 比对冻结输入。编译失败、换依赖、换版本或修改参数后重新展示并确认；不在旧确认下自动修复输入。上述本地计划工具的纯函数不代替真实飞书身份鉴权、确认原子消费或提交幂等。独立Bot双APP入口已部署专用最终参数确认回调，使用本人的原卡、nonce、版本和冻结摘要核验；它不调用本地计划工具伪造就绪收据。

## 3. 编译与验证 M100

普通软件准备或专项编译时，在工作站独立目录，用固定 Commit、配套 SDK/消息库/传感器开发包、明确的 `conan_shared` 和已核验工具链调用原 `build.sh`。独立Bot双APP入口则在确认后发布两份隔离配方，由原Jenkins执行实际编译与打包，不先重复一次本地冷编译；以该执行器保存的真实CI/Jenkins收据恢复，不能伪造本地CMakeCache。不修改业务分支或共享脚本，不在模糊版本上无限重试。`scripts/prepare_pcm_components.py` 可准备隔离配方；准备不等于编译或发布。

ON/OFF 对比固定相同业务提交、公共依赖和工具链，只在本次独立配方中设置明确模式及唯一版本。不把任务目标映射为宏值。保存真实 CMakeCache、生成锁、日志、SO 摘要与实际使用包身份；比较缺少 PREV 的预构建锁时另补实际消费包证据，不重写原锁或伪装相同。

源码、产物和日志只留 Linux；限制资源，串行构建两版并只读复用已验证依赖，清理本次容器/临时认证，不影响其他任务或修改共享缓存。编译通过不等于台架运行、预测一致或评测通过。

## 4. 按所选范围发布、发包

仅 SO 交付不强制发布 Conan。需要供 Jenkins 选择或用户明确要求发布时，读[组件 CI 发布](component-publication.md)：仅在原组件项目的独立 `codex/` 分支、用已有 CI 服务账号发布本次精确 recipe；不覆盖 stable、旧版本、共享模板或其他分支。回读真实修订、源码提交、宏和摘要后才登记 remote_recipe。recipe 发布不代表二进制已上传。

固定原 Job 为 `TRANSIT/XCU/SCM/CCU-ACORE-RELEASE-BUILD`。APP_VERSION 选择 M100 配方，Job 没有独立 EVAL 开关；Job 可能据配方重新编译。沿用[原流程](upstream-workflow.md)和[通知路由](notification-routing.md)，按新计划 `jenkins_modes` 仅提交选中的一次或两次，不改共享 Job。

基线/组件/依赖输入先核验；BUILD_REPLAY=true 用于复现基线，不是 dump 开关。UPLOAD_ALL_PACKAGE=false；APP/标准锁仍照常上传。核对基线制品属性不含继承镜像、Portal 字段为空，不只看表单空值。实际通知随真实 APP 构建次数，不固定发两张卡。

参数提交前依据原集成 package.lst 区分打包组件与传递依赖。清单中的组件换版必须放入 APP_VERSION，不能只用 LOCKED_LIBS 覆盖而保留基线旧条目；两栏不重复同名组件。用原选择和打包校验函数检查预期引用一致后再提交，不能到 Jenkins 长时间编译结束才发现清单冲突。具体失败与修正证据见[组件选择](component-selection.md)。

展示可审阅的最终参数、源码/配方和副作用后沿用本次有效授权。每次提交先记录唯一意图，绑定本次真实队列/构建编号；结果不明查原提交，不重复 Build、不用 lastBuild 猜身份。失败不自动重试或取消其他人的任务。

## 5. 当前由用户手动转交台架材料

记录APP、Lockfile、构建链接和各SO来源，先完成独立软件交付。当前由用户手动选择并转发一张构建结果卡，作为既有台架评测入口的软件材料，再补数据、依赖与可选配置，并单独确认台架执行。生产尚未实现构建任务与台架任务自动关联、自动迁移材料或发包后自动排队；后续整合另行开发。不得将软件构建确认用于台架派发。若在同一 APP 上分别运行 OFF、ON，各建一个冻结材料快照并分别确认、串行排队，分别交付结果；仅编译/上传/替换草稿材料不产生台架任务。

每次执行核对本人资产及当前台架装配，不能把“上次成功配置”当作当前板端状态。共用 APP 必须对齐公共 SDK、消息库、相机/雷达库和本次 YAML；缺接口不能只换 M100。评测需要 ON 能力、正确运行配置、真实预测结果和匹配真值，但 ON 不强制计算指标。

原始 APP 的打包模式与本次实际装配模式分开追溯：换装 ON SO 的候选需有新的装配记录和来源，不能仍按基础包 OFF 状态误判，也不能冒称未经改变的官方 ON APP。详细字段与边界见[工作流上下文](workflow-state.md)；这不是绕过生产官方模式保护的理由。

真实执行保持材料卡确认、全局 FIFO 与 Runner 原子 JSON 锁；构建确认不是台架确认，不重复已完成帧。该Skill仍是独立软件准备能力。Bot已接入单独的PCM双APP入口，不等于原台架材料卡已集成源码发包，也不等于两份新APP已通过实机回放。

历史双包比较与[实发记录](verified-run-20261106.md)保留原结论；只有显式双 APP 才做成对比较，不改阈值或扩大差异允许名单来称成功。源码、计划、编译、发布、发包、台架与评测分别报告状态。
