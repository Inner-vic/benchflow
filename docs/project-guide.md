# 台架评测统一入口

交接仓库：[developer-handover/bench-evaluation](https://github.com/Inner-vic/benchflow)。新接手人先读[部署与接手清单](../docs/09-部署与接手清单.md)、[当前基线](../docs/06-部署基线.md)及[收录范围](../docs/10-仓库收录与来源.md)。本库用于源码维护和多设备交接，不直接部署到现网。

飞书私聊收集APP链接、SO/YAML和数据路径，用户在材料卡确认后，由Linux工作站准备材料、串行操作台架，交付回放目录或云端评测TXT。Windows运行CC Connect和受限Codex解析，Linux保存业务状态及文件。其他项目共用Bot时业务记录独立，板端必须统一FIFO；不属于本项目的评测链路不合并。

## 功能职责

软件发包与台架执行采用独立的输入、确认和任务记录。

| 功能 | 输入 | 交付 |
| --- | --- | --- |
| Jenkins 发包 | 源码分支、软件版本、构建类型和组件版本配置 | 普通 APP、对应 Lockfile、构建链接及正式卡片 |
| 台架回放与评测 | APP、配套 SO、数据集及可选 YAML | 回放结果目录，按任务目标交付评测 TXT |

用户转发构建结果卡，将软件来源交给台架材料入口，再补齐材料并确认执行。依赖替换和 [M100 准备](18-M100编译流程.md)属于台架材料流程。普通 APP 后另编 ON M100 是目标步骤，独立评测模式与材料装配尚待适配；软件构建确认与台架执行确认分别保留。自动关联构建与台架任务尚未实现。

Jenkins 发包已完成当前规范的代码适配和隔离回归，待部署验收，详见[功能说明](17-Jenkins发包.md#实现状态)。原 Bot、独立软件状态库及 worker 的运行依据见[部署与验收记录](16-双版本构建确认与派发.md)。`modules/jenkins-input-card/` 保留早期输入模块与兼容接口。

源码维护与生产部署分别管理；运行目录、认证和业务数据库的变更遵循既有发布流程。

## 边界

凭据、业务SQLite、APP/SO、数据集、预测、报告和现场审计原件留运行环境。补丁CC Connect、原生适配器、评测器二进制及Docker/Conan环境仍须按既有部署取得并核对摘要；克隆仓库不等于可从零自动重建四设备环境。

真实执行要求有效本人卡片确认；正常资源忙继续排队，未知结果待核验。通知、材料修复或评测失败不构成重跑台架的依据。

仓库记录的既有 M100 自动链路读取 APP 构建记录，按官方 ON/OFF 调用原 `build.sh`；OFF 评测请求会提示不匹配。原实现和验证记录见[M100 官方构建](11-M100官方构建与自动编译.md)，普通 APP 后编译评测 M100 的目标流程见[评测编译流程](18-M100编译流程.md)。PCM测试1与原主入口的云端策略分别维护，部署依据见[当前基线](06-部署基线.md)。

静态检查运行 `python tools/check_repository.py`，规则自测运行 `python -m unittest discover -s tools/tests -q`。Linux定向测试见运维文档；测试通过不代表新包、物理台架、新电脑重启或云端实例均已验收。
