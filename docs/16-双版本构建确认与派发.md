# PCM 双版本构建

> 2026-11-17起，当前操作统一见[Jenkins 发包](17-Jenkins发包.md)，按原流程构建普通APP。本页保留此前实现和验证记录，相关派发接口不作为当前默认执行器；本次未调整或部署线上Bot。

本功能在“台架评测”Bot内提供独立的软件构建入口：工程师填写源码分支、软件版本和组件引用，核对最终参数后，一次确认生成普通版OFF与评测版ON两份APP，并在私聊中交付两张结果卡。

2026-11-13已用SW00F1真实完成校验、确认、配方发布、两版Jenkins发包和飞书交付。这里只说明软件构建；不自动启动台架回放或指标评测。


## 当前功能边界：两个阶段，人工转交

| 阶段 | 输入和交付 | 当前状态 |
|---|---|---|
| 独立Jenkins双版本构建 | 源码分支、软件版本、组件引用 → OFF/ON两份APP及两张结果卡 | 已实现，本次已真实验收 |
| 台架评测 | 用户转发选定的一张构建结果卡作为软件输入，再按既有材料流程准备数据、SO和可选配置，确认后回放/评测 | 已有独立流程，本次未重新执行台架验收 |
| 两阶段自动整合 | 发包成功后自动关联台架材料、自动建台架任务或派发台架 | 尚未实现，本次不纳入 |

同一个Bot提供入口，不代表两个阶段已经自动串联。**当前衔接动作是用户手动选择并转发其中一张OFF或ON结果卡。**转发只是台架评测的材料输入，仍须按既有流程核齐数据和依赖，并单独点击台架材料卡“确认执行”。构建确认不能代替台架确认。

```text
阶段A：构建配置 → 确认构建 → OFF/ON APP → 两张构建结果卡
                                           │
                              用户手动选择并转发其中一张
                                           ↓
阶段B：台架材料输入 → 补充数据/依赖/配置 → 确认执行 → 回放/评测
```

目前没有构建任务与台架任务之间的自动关联、材料自动迁移或跨阶段自动续执行；后续整合另行设计和提交。发包成功不能标记台架阶段成功。

## 1. 如何使用

私聊机器人发送“PCM双版本构建”，填写以下信息：

| 输入 | 规则 |
|---|---|
| 源码分支地址 | 当前支持uroad仓库的GitLab分支链接；每次解析并冻结实际Commit，不固定dev-315-eval |
| 软件版本 | 本次BASE_LINE，4位十六进制字符，可带SW前缀；新任务留空，不沿用历史版本 |
| 构建类型 | release/debug，初始release；本次真实验收使用release |
| 组件版本配置 | 下列三项必须填写精确引用，其他组件可逐行追加；可回填本人上次确认配置 |

```text
conan_shared/<版本>@livc/release-schu
uroad_m100/<版本>@livc/stable
dag_compiler/<版本>@livc/stable
```

这些是提示模板，不是真实版本；占位符、缺项或范围版本不能提交。软件ID按当前AVM范围固定0111，无需输入。ULTRA/MAX来自所选且核验过的成功基线，不只修改包名。

1. 点击“校验构建配置”，只读取源码、成功基线、锁文件及配方，不编译或发包。
2. 原卡展示最终参数，包括源码Commit、产品基线、两份M100引用及OFF/ON完整Jenkins参数。
3. 核对后点击“确认构建两版APP”，才建立软件构建任务。返回修改会使旧参数确认失效。
4. 后台依次完成组件配方发布、OFF发包、ON发包；两张结果卡原位更新。
5. 每版成功后交付LIVC APP下载链接、集成Lockfile和Jenkins构建链接；原参数卡显示整体完成。

打开、编辑或校验不会更新本人“已确认配置”记忆，也不会触发台架。已提交任务冻结输入；后续修改属于下一次任务。构建号由Jenkins生成。

## 2. 各节点负责什么

| 节点 | 职责与连接 |
|---|---|
| 飞书 | 收集输入、接收真实按钮确认、展示两版进度与结果链接 |
| Windows入口机 | CC Connect维持飞书长连接；通过SSH将受信事件转交工作站，不保存APP、源码或构建业务库 |
| Linux工作站 | 参数解析、本人草稿与确认、独立软件FIFO、派发收据、恢复与卡片交付；通过HTTPS访问GitLab、Jenkins、JFrog |
| GitLab组件项目CI | 在独立codex/分支发布本任务的两份精确Conan recipe，使用原CI服务身份 |
| 原Jenkins Job | 按最终参数实际编译M100并打包APP；先OFF、后ON |
| JFrog | 保存组件配方、APP和Lockfile；卡片交付原下载链接 |

构建过程不经过LPAI，不占台架，不进入硬件FIFO。源码仓库与交接仓库是不同对象：前者用于取源码和组件CI，后者用于维护本Bot功能的程序、文档与测试。

## 3. M100与ON/OFF怎么生成

`uroad_m100`输入是配方/版本基准，不代表复用历史SO。系统据本次固定Commit和公共依赖，生成任务唯一的两个私有引用，在隔离配方中明确`WITH_EVAL_DUMP=OFF/ON`。最终APP_VERSION分别选中相应M100，公共参数保持一致。

GitLab发布分支形如`codex/pcm-bot-b<草稿标识>r<修订>`。只增加本任务的CI及配方文件，不改业务分支、共享模板、共享Jenkins Job或既有stable版本。发布recipe不等于二进制编译通过；原Jenkins负责实际编译与打包，不先在工作站重复冷编译一次。

若需使用与源码声明不同的回放版X-Lidar，仅在显式成功基线、精确锁文件和远端配方均能证明来源时，允许把该引用绑定到本次两个私有M100配方，并在最终参数中展示调整依据。其他未经证明的依赖冲突继续拒绝。

`WITH_EVAL_DUMP`决定M100是否编入评测数据输出能力；运行时`eval_dump.enable`及具体输出配置是另一层。ON版APP构建成功，不等于已开启运行输出或完成指标评测。普通软件准备Skill原有的仅SO、一份APP加两份SO等流程仍保留，与这个明确双APP入口分开。

## 4. 工作站目录与部署

| 内容 | 位置 |
|---|---|
| 网关程序 | `/mnt/data/bench-eval/service/gateway` |
| 独立软件业务库 | `/mnt/data/bench-eval/state/pcm-dual-build.sqlite3` |
| 本人冻结参数 | `/mnt/data/bench-eval/users/<本人标识>/builds/PB-<编号>/confirmed-review.json` |
| 功能开关 | 网关`runtime/pcm-dual-validation.json` |
| 原子派发与恢复记录 | 独立业务库中的pcm_build_jobs、pcm_build_steps |
| APP、Lockfile、CI日志 | JFrog、GitLab和Jenkins各自保存，Bot记录精确身份并给链接 |

在已有网关和已适配CC Connect的环境中增量部署，不是从空系统一键安装：

1. 核对实际源码与在途任务，备份精确程序、开关和一致性数据库；不覆盖他人改动。
2. 安装仓库`workstation/gateway/bench_gateway/pcm_*.py`中本功能的8个模块，按审核差异给cc_agent增加独立路由；不要通配覆盖pcm_test1等其他项目模块。
3. 将Skill的source_build_discovery.py、resolve_pcm_input.py、pcm_existing_job.py、prepare_pcm_components.py放入网关`extensions/pcm-dual-validation/scripts/`；同目录放入examples/ci-20261106/internal_pcm_pair/publish_recipes_ci.py作为受限发布模板。程序在生成本任务payload时重写经核对的绑定，不能直接重跑历史示例。
4. 将`workstation/systemd/bench-pcm-build.service`按现场路径安装为用户级单元。复用已有加密GitLab、Jenkins及团队JFrog认证，不把凭据写入Git或模板。
5. 参考`config/pcm-dual-validation.example.json`创建现场开关，先保持关闭，启动独立软件服务并完成只读预检；核对其他业务与本人草稿未变后再启用两项开关。
6. 使用真实本人卡片验收，不伪造按钮回调或重放生产确认。仓库更新不等于生产部署，合并后不能自动覆盖现网。

```sh
systemctl --user status bench-pcm-build.service
journalctl --user -u bench-pcm-build.service
```

`enabled`控制独立卡片入口，`jenkins_enabled`控制确认和派发；上线需均为true。示例默认false。维护阻止领取新任务；已提交构建按原身份继续查询。关闭总开关会停止后续查询，不等于取消Jenkins，须先检查在途任务。

## 5. 排队、恢复和通知

- 软件构建使用独立FIFO与单worker，不接管硬件FIFO、Runner或生产bench.lock。软件worker自己的进程保护文件与台架JSON锁不同。
- 真实确认绑定本人、会话、原卡、草稿版本、nonce及冻结摘要。重复点击不新增任务；分支变化须重新校验。
- 对外写入先保存意图。响应丢失时只查本次原分支、流水线、队列和完整参数；不存在或多义则待核验，不盲目重新POST。
- OFF失败停止ON；ON失败保留OFF成功产物。恢复只续查未完成阶段，不重跑已完成OFF。
- 制品索引延迟有界等待600秒，只继续读取，不重新Build。
- 结果卡使用稳定发送身份；通知失败仅续交付，不重建软件。Jenkins原群通知保持，Bot私聊另有本次两张结果卡。
- 认证失效明确提示管理员处理，不承诺永久免登录；回退只恢复本次程序，不回滚业务数据库或取消其他人的构建。

| 项目 | 2026-11-13结果 |

| 普通版OFF | Jenkins #3016成功，SW00F1 APP与Lockfile已核对，约15分46秒 |

| 台架 | 未刷包、未回放、未评测；不能据发包成功宣称运行通过 |

最终修订后定向测试：独立卡片/路由41项、软件派发20项、Skill93项，合计154项。另有此前旧卡预览7项通过；不把重跑次数叠加成测试覆盖总数。

桌面连接曾退出并留下待核验租约。恢复时独立核实旧进程及套接字已不存在，备份并通过原所有权接口释放单个租约，再启动既有计划任务；未按超时自动清理。旧进程退出的确切原因尚未查明，不能宣称长时间无人值守稳定性已根治。
